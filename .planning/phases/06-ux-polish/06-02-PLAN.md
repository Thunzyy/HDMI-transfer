  <action>
Replace the `drawBits(bits)` function with the 3bpp version. The current function reads 1 bit per block and draws BLACK or WHITE. The new function reads 3 consecutive bits per block and maps them to independent R, G, B channels.

**Replace the drawBits function with:**
```javascript
function drawBits(bits) {
    let bitIdx = 0;
    for (let r = 0; r < ROWS; r++) {
        const startY = r * BLOCK_SIZE;
        for (let c = 0; c < COLS; c++) {
            // Read 3 bits: R, G, B (matching Python unpackbits order)
            const rBit = bits[bitIdx++];
            const gBit = bits[bitIdx++];
            const bBit = bits[bitIdx++];
            // Pack into ABGR uint32 (little-endian: 0xAABBGGRR)
            const color = 0xFF000000
                | ((bBit ? 0xFF : 0x00) << 16)
                | ((gBit ? 0xFF : 0x00) << 8)
                | (rBit ? 0xFF : 0x00);
            const startX = c * BLOCK_SIZE;
            for (let y = 0; y < BLOCK_SIZE; y++) {
                const rowOffset = (startY + y) * WIDTH + startX;
                buf.fill(color, rowOffset, rowOffset + BLOCK_SIZE);
            }
        }
    }
    ctx.putImageData(imageData, 0, 0);
}
```

**Critical endianness note:** The Uint32Array view of ImageData stores pixels in native byte order. On little-endian systems (all x86/ARM), the 32-bit integer `0xAABBGGRR` maps to bytes `[R, G, B, A]` in memory. This matches the existing `BLACK = 0xff000000` (R=0, G=0, B=0, A=255) and `WHITE = 0xffffffff` (R=255, G=255, B=255, A=255) convention already in the code.

The bit order (R first, then G, then B) matches Python's `np.unpackbits` which unpacks MSB-first, and the `reshape((blocks, 3))` which assigns channel 0=R, 1=G, 2=B in the RGB array.

**Also update `bytesToBits`:** No changes needed -- it already unpacks MSB-first matching Python's `np.unpackbits`. It will now be called with a larger frameBytes array (12150 bytes -> 97200 bits) which matches the new `state.bits` size.
